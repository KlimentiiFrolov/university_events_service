# Сервис регистрации на университетские мероприятия

Учебный проект по курсу **«Технологии сетевого программирования»**.

Проект развивается поэтапно в рамках лабораторных работ. Предметная область — регистрация пользователей на университетские мероприятия: каталог событий, запись участников, работа организатора, рекомендации и уведомления в реальном времени.

## Структура репозитория

Корень репозитория тонкий: единственный файл оркестрации `docker-compose.yml`, документация и по одной папке на микросервис. Каждая папка-сервис **самодостаточна** и повторяет структуру примера `Session_Auth` (свой `src/`, `Dockerfile`, `pyproject.toml`, `uv.lock`, `.env.template`, свой `alembic/` там, где нужна БД).

```text
.
├── docker-compose.yml          # единственная точка оркестрации
├── README.md
├── docs/                       # задание по курсу отчёты по лабораторным
│   ├── course-assignment.pdf
│   └── lab-00 … lab-06/
├── scripts/                    # вспомогательные и демонстрационные скрипты
│                               #   (в т.ч. gen_proto — генерация stub'ов)
├── proto/                      # единственный источник gRPC-контрактов (.proto)
│   └── recommendation.proto
│
├── api_service/                # FastAPI: каталог, регистрация, авторизация, SSR
│   ├── Dockerfile
│   ├── pyproject.toml
│   ├── .env.template
│   ├── src/
│   └── tests/
│
├── recommendation_service/     # gRPC-сервис рекомендаций
│   ├── Dockerfile
│   ├── pyproject.toml
│   ├── .env.template
│   ├── src/
│   └── tests/
│
├── notification_service/       # RabbitMQ consumer + WebSocket
│   ├── Dockerfile
│   ├── pyproject.toml
│   ├── .env.template
│   ├── src/
│   └── tests/
│
└── notification_client/        # клиент уведомлений по WebSocket
    ├── Dockerfile
    ├── pyproject.toml
    ├── .env.template
    ├── src/
    └── tests/
```

### Что где хранить

- `docs/` — задание по курсу, отчёты, схемы и материалы по каждой лабораторной.
- `proto/` — `.proto`-файлы, единственный источник истины по gRPC-контрактам.
  Сгенерированный код здесь **не хранится** — он лежит внутри сервисов (см. ниже).
- `<service>/src/` — код сервиса. Внутренняя раскладка — по образцу `Session_Auth`:
  `core/` (конфиг, БД, логгер, безопасность), `api/` или `grpc/` (транспортный слой),
  `services/` (бизнес-логика), `repositories/` (доступ к данным), `models/`, `schemas/`,
  `alembic/` (миграции). Появляется по мере реализации лабораторных.
- `<service>/tests/` — модульные и интеграционные тесты сервиса.
- `<service>/.env.template` — значения окружения по умолчанию (коммитится);
  реальный `.env` не коммитится.
- `<service>/Dockerfile` — образ сервиса, контекст сборки — папка самого сервиса.
- корневой `docker-compose.yml` — поднимает инфраструктуру (PostgreSQL, RabbitMQ)
  и все сервисы.

### Планируемая внутренняя структура сервисов

Ниже — ориентир, к которому идёт каждый сервис. На старте внутри `src/` пусто.

- **api_service** — `core/`, `api/` (роутеры: `events`, `registrations`, `auth`, `organizer`),
  `services/`, `repositories/`, `models/` (+ `mixins/`), `schemas/` (+ `exceptions/`),
  `clients/` (gRPC-клиент рекомендаций, publisher в RabbitMQ), `alembic/`, `ssr/templates/`.
- **recommendation_service** — `core/`, `grpc/` (реализация servicer'а),
  `grpc/generated/` (сгенерированные из `proto/` `*_pb2.py` / `*_pb2_grpc.py`, коммитятся),
  `services/`, `repositories/`, `models/`, `schemas/`, `alembic/`.
  gRPC-клиент рекомендаций внутри **api_service** использует те же стабы,
  сгенерированные в `api_service/src/clients/generated/`.
- **notification_service** — `core/`, `consumers/` (обработчики очередей RabbitMQ),
  `websocket/` (эндпоинты, менеджер подключений), `services/`, `schemas/`.
- **notification_client** — `core/`, точка входа `main.py`.

## Архитектура: почему так и какие трейдоффы

Выбрана плоская раскладка «папка на микросервис + один `docker-compose.yml`». Общего Python-пакета нет: совпадающий инфраструктурный код (конфиг, логгер, обёртки над БД/RabbitMQ, схемы событий RabbitMQ) сознательно дублируется между сервисами. Исключение — gRPC-контракты: `.proto` лежат в одном общем `proto/` (см. отдельный раздел ниже).

### Плюсы

- **Чистое разделение ответственности.** Логика одного сервиса физически не может обратиться к другому напрямую — только через REST / gRPC / очередь. Это ровно то, что проверяется в курсе.
- **Независимые зависимости и релизы.** У каждого сервиса свой `pyproject.toml` / `uv.lock`; обновление библиотеки в одном сервисе не задевает остальные.
- **Простой и быстрый Docker-билд.** Контекст сборки маленький, кэш слоёв не инвалидируется из-за изменений в соседнем сервисе. Dockerfile — почти копия рабочего из `Session_Auth`.
- **Низкий порог входа.** Каждая папка — знакомый по `Session_Auth` проект; можно открыть один сервис и работать, не держа в голове весь монорепо.
- **Лёгкий вынос в отдельный репозиторий** позже — папка уже самодостаточна.

### Минусы

- **Дрейф дублированного кода.** Исправление в `core/` одного сервиса не попадает автоматически в остальные; «одинаковые» файлы со временем расходятся.
- **Схемы событий RabbitMQ не проверяются на этапе импорта.** Payload сообщений описан в каждом сервисе отдельно — рассинхрон ловится только тестами/рантаймом. Это осознанный выбор, а не недоработка — обоснование ниже. (gRPC-контракты этой проблемы лишены — см. ниже.)
- **Нет сборки и линтинга «одной командой».** `ruff`, `pytest`, `uv sync` запускаются в каждой папке (или через скрипт-обёртку в `scripts/`).
- **Дублирование окружения.** Общие параметры (Postgres, RabbitMQ) повторяются в нескольких `.env.template`; при смене — править везде.
- **Больше boilerplate на старте** — по `Dockerfile`, `pyproject.toml` и `core/` на каждый сервис.

## gRPC-контракты: общий `proto/`

`.proto`-файлы вынесены на один уровень с сервисами, в каталог `proto/` — это **единственный источник истины** по gRPC-контрактам. Сам сгенерированный код (`*_pb2.py`, `*_pb2_grpc.py`) в `proto/` не хранится.

Процесс изменения контракта:

1. Правим `.proto` в `proto/`.
2. Запускаем `python -m scripts.gen_proto` (обёртка над `grpc_tools.protoc`).
   Скрипт кладёт свежие стабы **в каждый сервис, который использует контракт**:
   - `recommendation_service/src/grpc/generated/` — для реализации servicer'а;
   - `api_service/src/clients/generated/` — для клиента.
3. Коммитим и `.proto`, и обновлённый сгенерированный код в одном PR.

Сгенерированные файлы **коммитятся** в репозиторий (не в `.gitignore`): diff контракта виден в ревью, а сборка образа не требует `protoc` и происходит из готовых `.py`.

### Почему так работает

- Стабы генерируются **внутрь** каждого сервиса, в отдельный подпакет `generated/`, и не перемешиваются с рукописным кодом.
- `Dockerfile` и контекст сборки не меняются: `protoc` в образе не нужен, `COPY . /app` просто забирает уже сгенерированные `.py`. Пересборка контейнера после изменения `.proto` — обычная пересборка от изменения исходников, новых слоёв/зависимостей не появляется.
- Содержимое образа меняется ровно на дельту контракта (новые сообщения/методы), больше ничего.
- Версии `grpcio` / `protobuf` у сервисов независимы; каждый генерирует стабы своей версией `grpcio-tools` из dev-группы.

### Трейдоффы

**Плюсы**

- Один источник истины: `.proto` нельзя «поправить у себя» — он общий, рассинхрон контракта невозможен by design.
- Ревью контракта — это diff одного файла в `proto/`; сгенерированный diff рядом показывает эффект.
- Сборка образов остаётся простой и быстрой: без `protoc`, без плагинов, без сетевых зависимостей на этапе build.
- Легко подключить третий сервис к тому же контракту — добавить его в цель генерации.

**Минусы**

- Сгенерированный код продублирован по сервисам и **должен быть пересобран вручную** после правки `.proto`. Забыли запустить `gen_proto` — стабы и контракт разъезжаются. Лечится pre-commit хуком или проверкой в CI (`gen_proto --check`: сгенерировать во временную папку и сравнить).
- Разбухание diff'ов: механически сгенерированные файлы шумят в PR (можно пометить `linguist-generated` / свернуть в ревью).
- Если сервисы возьмут сильно разные мажорные версии `protobuf`, сгенерированный код может оказаться несовместимым по рантайму — нужно держать версии близкими.
- Чуть больше движущихся частей, чем «`.proto` прямо в сервисе»: отдельный каталог + скрипт генерации, который надо помнить запускать.

## Схемы событий RabbitMQ: по сервисам

В отличие от gRPC-контрактов, схемы сообщений для событийной коммуникации (Pydantic-модели payload'а) **намеренно продублированы** по сервисам: своя копия в `api_service` (publisher) и в `notification_service` (consumer). Общего каталога, аналогичного `proto/`, для них нет.

### Почему так

- **Править всё равно придётся оба сервиса.** Меняется формат сообщения → нужно и по-новому его публиковать, и по-новому разбирать на стороне consumer'а. Единая схема не убрала бы эту работу: обработчики, миграция «старых» сообщений в очереди, тесты — всё равно правятся с двух сторон. Выигрыш от общего источника здесь куда меньше, чем у `.proto` (где из одного файла генерируются обе стороны автоматически).
- **Нет кодогенерации.** Для JSON-сообщений RabbitMQ нет шага вроде `protoc`, который бы оправдывал отдельный каталог и скрипт. Схема — это просто `pydantic.BaseModel`, писать его руками в обоих местах дёшево.
- **Слабая связанность по событиям — это цель.** Consumer и publisher эволюционируют независимо; допускать расхождение версий сообщения (consumer читает и новый, и старый формат в переходный период) проще, когда схемы отдельные.
- **Контекст различается.** Publisher'у нужна модель на выход, consumer'у — на вход + служебные поля (routing key, попытки ретрая). Это не один и тот же класс.

### Трейдоффы дублирования схем

**Плюсы** — ноль дополнительной инфраструктуры; сервисы полностью автономны; переходные несовместимости форматов допустимы by design.

**Минусы** — рассинхрон полей ловится только интеграционным тестом или в рантайме; нужна дисциплина «менять обе копии в одном PR»; нет машинной проверки совместимости. Смягчение: контрактный тест в CI, который гоняет реальное сообщение publisher'а через схему consumer'а.

### Про инфраструктурный код

Небольшие общие модули (`config` / `logger` / `db`, ~150 строк) осознанно оставлены дублированными по сервисам — это дёшево и стабильно. Если дублирование начнёт мешать, следующий шаг — вынести их в общий устанавливаемый пакет (`packages/common/`), а не в `PYTHONPATH`-хак.

## Git workflow

Для проекта из двух человек отдельная постоянная ветка `develop` не нужна. Используем три уровня:

1. `main` — только завершённое и сдаваемое состояние.
2. `lab/N-name` — интеграционная ветка текущей лабораторной.
3. `feature/...`, `fix/...`, `docs/...`, `test/...` — короткие ветки конкретных задач.

Feature-ветки вливаются Pull Request'ами в ветку лабораторной. Когда лабораторная готова целиком — итоговый PR `lab/N-name -> main`, после merge ставим тег:

```bash
git switch main
git pull origin main
git tag -a lab-1 -m "Lab 1 completed"
git push origin lab-1
```
